# 工作中沟通的要点

向上、业务方、技术方、平级、向下，以及换位思考

::: info

**本文的定位**：一篇个人职场沟通笔记，按沟通对象拆开整理。每一类对象在乎的东西不一样，沟通的打法也就不一样。

沟通这件事，难点不在嘴上，在心里得装着对方。想清楚对面的人最关心什么、最怕什么，自然就知道该怎么开口、怎么把事办成。最难的是建立信任：让别人相信你说的话，思路才能对齐。信任有了，后面很多事都好办。

:::

```text
老板：在乎结果与风险 → 给结论、给选项、给预期
业务方：在乎进度与效果 → 给确定性、给替代方案
技术方：在乎边界与责任 → 对齐接口、落文档、留痕
平级：在乎分工与脸面 → 边界清晰、公开认可
下属：在乎目标与成长 → 讲为什么、给标准、给反馈
```

## 零、核心原则

先说六条通用的，不管对面是谁都绕不开。

**先听后说。**先理解对方的诉求和处境，再表达自己。这一步做得好不好，直接决定后面能不能快速达成一致。

**换位思考。**“如果我是他，我想听到什么？”这是卸掉对方防备心的关键，第六章单独展开。

**情绪稳定。**情绪上头时说的每句话，事后都要用十句话来弥补。所以工作中尽量把情绪放一边，就事论事。

**少即是多。**抓重点。每个人每天要处理大量信息，越精炼越容易被记住。人人都是本行的专家，也是他行的外行，不能假设对方听得懂你讲的东西。浅显表达、层层深入，比一次倒一大堆细节强得多。

**闭环。**说过的事要有回音，承诺过的事要有交付，别人判断你靠不靠谱，看的就是这个。

**小杖受，大杖走。**不关键的事情充分认同、大加赞赏；关键性问题寸步不让。有个万能句式：

::: info

“对于你的 xxx 观点我非常认同，这个问题确实本质是 xxx，你提的方案特别合理，我也是这么觉得的，不过……”

:::

关键全在这个“不过”上。前面都是认同和铺垫，转折后面才是你真正要坚持的东西。

## 一、对上：让老板省力又放心

::: tip

**核心目标：**让老板做决策省力，对你放心，建立双边信任。信任感越弱，老板越喜欢追细节；信任感越强，越容易达成一致。与老板建立充分信任，是有效沟通的前提。

:::

老板在乎的是结果和风险。老板不怕问题，这个层级存在的意义就是解决问题；他真正担心的是“不知道你到底要他干什么”，信息差会带来决策失误。

所以向上沟通的底层逻辑就三条：给结论、给选项、给预期。

<table>
<tr><th>要点</th><th>说明</th></tr>
<tr><td>结论先行</td><td>第一句话就抛结论，别铺垫：“风险是什么、我建议怎么办”。</td></tr>
<tr><td>带方案提问，不甩问题</td><td>“老板这个怎么办”价值不大。换成：“目前有 A/B 两个方案，我倾向 A，理由是……您怎么看？”</td></tr>
<tr><td>管理预期，主动同步</td><td>进度主动报，坏消息更要早说。风险管控是管理者的基本功，这个做不好是要下台的。</td></tr>
<tr><td>理解老板的 KPI</td><td>你说的话要能帮他向上交代。对上级有用的信息，等于对上级的上级有用的信息。</td></tr>
<tr><td>不越级、不隐瞒</td><td>有异议当面说，决策之后坚决执行。到这一步，风险已经完成了上移。</td></tr>
</table>

## 二、对业务方：让人觉得配合省心

::: tip

**核心目标：**让对方觉得研发配合起来很省心，由此建立信任。

:::

业务方不关心技术怎么实现，他关心的是：我的需求能不能按时上线，出了问题能不能找到人，效果符不符合预期。他要的其实是一个靠谱的合作伙伴，关注点就两个：进度和效果。

<table>
<tr><th>要点</th><th>说明</th></tr>
<tr><td>讲业务语言</td><td>“缓存击穿”说成“用户高峰期会慢、我们能扛住”。</td></tr>
<tr><td>需求与业务充分对齐</td><td>反复确认“你要解决的问题是什么”，先共识目标再谈实现。这也是技术方案要拉业务一起评审的原因。</td></tr>
<tr><td>给确定性，让对方有掌控感</td><td>能做、不能做、做了有什么代价，一次说清。每个人都在求确定性，最烦模棱两可的结论，推己及人。</td></tr>
<tr><td>及时暴露风险和成本</td><td>出问题没关系，做不到就直说做不到，同时给业务替代方案。能内部消化的问题别扩大化，风险能分担出去的一定要及时分担。</td></tr>
<tr><td>求同存异</td><td>研发面对业务整体偏弱势。先谈“事情能做”这个大方向，再切怎么做，会好谈很多。</td></tr>
</table>

## 三、对技术方：专业、边界清晰、留痕

::: tip

**核心目标：**减少摩擦和扯皮，让流程高效，通过多次协作建立信任，但要注意边界。

:::

技术方之间最忌讳互相猜。大家真正关注的是边界和责任。做法归结起来：专业，边界清晰，关键事项留痕，不给扯皮留空间。

<table>
<tr><th>要点</th><th>说明</th></tr>
<tr><td>对齐接口与边界，落到文档</td><td>谁来做什么、API 长什么样、字段含义、异常处理，全部落文档。</td></tr>
<tr><td>尊重对方的技术栈和约束</td><td>不轻易说“这个很简单”。我们不了解别人的系统，就像别人也不了解我们的一样。</td></tr>
<tr><td>用数据和日志说话</td><td>出了问题带上日志、trace、复现路径，给出明确定性，不靠嘴说。</td></tr>
<tr><td>关键决策留痕</td><td>会议结论发群里，这个大家早就驾轻就熟了。</td></tr>
<tr><td>分工边界必须清晰</td><td>每次合作先弄清楚事情归属哪个域，防住边界模糊地带的坑。但如果是我们主 R 的项目，要会打太极把对方绕进来，因为我们求的是大结果。最难的就是边界判定，需要时间积累。</td></tr>
<tr><td>扯皮不可避免，但不能被牵着走</td><td>模糊地带的事谁都不想做，最常见的推法是抛出一个宏大而正确的目标，把事情的属性搅浑，让你陷入“不做就不道义”的境地。这时候用“领域归属清晰之后做得更合理”来委婉拒绝：不是我不做，是归属清晰之后我来做更合理。</td></tr>
</table>

## 四、对平级：补位可以有，边界要守住

::: tip

**核心目标：**协作顺畅，互相补位，信任来自长期的靠谱和透明。

:::

平级之间最容易出的问题是“各扫门前雪”和“抢功甩锅”。这不好听，但必须面对：存量竞争下不会处理这一层，日后杂事就都堆到你头上。实在搞不定，小职级的时候可以在 1:1 里提给老板，把问题浮到水面，让老板去解决。

<table>
<tr><th>要点</th><th>说明</th></tr>
<tr><td>明确分工，边界清晰</td><td>出了问题别说“这不是我的问题”，而是说“这个问题的本质是 xx 域的设计不合理”，对事不对人。老板希望大家补位而不是泾渭分明，这中间有冲突：向上要营造出愿意补位的态度，实际投入要控制住，很考验分寸。</td></tr>
<tr><td>公开认可，私下提意见</td><td>功劳公开分。对爱抢功的同事多长个心眼，但无论怎样，公开场合护住彼此的脸面，不能撕破脸。</td></tr>
<tr><td>不抱怨，多提想法</td><td>“这事儿不对”后面一定要跟一句“我建议 xxx”。建议才是关键，它让大家看到你解决问题的能力。只吐槽不解决，纯消耗，旁观者对你的看法也会跟着消耗。</td></tr>
<tr><td>尊重各方节奏</td><td>沟通前想清楚这件事对他有什么价值、急不急。靠目标一致去绑定，而不是靠催，催没有用。</td></tr>
</table>

## 五、对下：赋能，不是管控

::: tip

**核心目标：**让团队清楚目标、有成长、有安全感，合理做利益和人的绑定。

:::

带人不只是发任务，更要让人愿意把事做好，向下沟通的核心是赋能。下面的同学在乎的东西很朴素：清晰的目标，加上看得见的成长空间。

<table>
<tr><th>要点</th><th>说明</th></tr>
<tr><td>讲“为什么”，不只讲“做什么”</td><td>忌讳机械执行。背景和目标讲清楚，同学才能自己判断怎么做是对的。</td></tr>
<tr><td>目标清晰可衡量</td><td>“你看着弄”这种模糊指令等于推卸责任。给方向、给标准、给 deadline。</td></tr>
<tr><td>给空间，不微操</td><td>目标和边界定好就放手，过度干预会磨灭主动性和成长。但不靠谱的同学还是要多盯着，过程管理是管理者必须做的。</td></tr>
<tr><td>及时反馈，正负都要</td><td>做得好要明确说哪里好，做得不好要具体指出怎么改。做错了没人说、做好了没人理，队伍就散了。</td></tr>
<tr><td>向上挡事，向外挡人</td><td>对上替团队争取资源和合理预期，对外挡住不合理的压力，当团队的盾牌。同时信息差要有：不确定的消息不下达，防止团队恐慌。</td></tr>
<tr><td>关注成长</td><td>定期聊“你想往哪发展、我能怎么帮你”，这就是 1:1 一直存在的价值，人愿意留下来多半是因为这个。团队标杆也要立，对全团队的信心都有帮助。</td></tr>
</table>

## 六、换位思考：从“我以为”到“他以为”

这一条值得单开一章。

换位思考的本质，是从“我以为”切换到“他以为”：我先懂你，你才愿意来懂我，最后找到双方都能接受的方案。

先分清两个概念：换位思考不等于利他主义。利他需要换位思考，换位思考却不一定要利他。利他很多时候是委屈自己迁就他人；换位思考最后还是落在“我”这个主体上，为我的利益服务。真正换到位的人，往往更快说服对方、更快推动事情，而推动事情本身就是我的利益。

换位思考的核心目的，是识别对方的意图。怎么识别？很难，但非常有价值，这里有一套可以照着走的清单：

<table>
<tr><th>要关注的点</th><th>要解决的问题</th></tr>
<tr><td>（核心）对方现在掌握多少信息？我有没有漏掉背景？</td><td>大多数沟通冲突的根源是信息差。你以为他懂背景，其实他不知道；你以为他看得到全局，其实他只看到了一个角落。</td></tr>
<tr><td>（核心中的核心）对方的核心诉求是什么？最怕什么？</td><td>每个人在不同场景下都有自己在乎的东西：老板在乎结果和风险，业务方在乎进度和效果，技术合作方在乎边界和责任，下属在乎清晰的目标和成长空间。</td></tr>
<tr><td>（技巧）如果我是他，听到我接下来这句话，第一反应是什么？</td><td>开口前先自己感受一遍。提意见、说“不行”、拒绝需求之前，先想好怎么让对方听得进去，而不只是“我说的对”。人是情绪动物，有时对方不是不认同你的道理，而是你的方式让他不舒服：觉得被否定、被施压、被忽略。你讲不过别人的时候，也是这种感觉。</td></tr>
<tr><td>（核心）我有没有解决对方的问题？</td><td>这一条会让对方感觉到尊重：这次沟通你是真的想解决他的问题，不是在硬推自己的事。以退为进，最后当然还是为了自己。</td></tr>
<tr><td>（技巧）有没有一种说法，能让对方更容易接受、更愿意配合？</td><td>同一个意思，对不同人说法完全不同。对老板：结论、风险、建议；对业务：能做还是不能做、要多久、付出什么；对技术：接口、边界、数据；对下属：目标、为什么、怎么衡量。想想每次跟老板 1:1，是不是都在这么换位。</td></tr>
</table>

换位思考的用处不止于沟通。项目推进、协同合作，甚至理解生活里各种看不懂的事，它都有帮助，也是日常做决策的指导方向。当然，识别错了就麻烦很大。这里面最重要的，是基于当前已知的信息判断对方的核心诉求，判断的过程就是自己跟自己反复博弈。

## 结语

回头看这几条其实是一个意思：把对方需要的信息给足，少让人猜，少让人等。技巧可以慢慢练，开口之前先想想对面那个人，这个习惯比技巧本身管用。
