# 领域建模实践：统一客户平台、资质中心与四色建模

统一客户 ID、资质生命周期与四色建模

::: info

**姊妹篇：**本文是[《技术方案设计指南：从架构演进到领域建模》](/tech-design-guide)的案例实践篇。前者系统介绍架构演进、DDD 与四色建模方法，本文用统一客户平台和资质中心展示这些方法如何落到具体业务模型中。

本文使用一个抽象案例：苹果品牌经营主体申请进入平台，在电商开设苹果官方旗舰店，同时在商业化平台开户投放广告。案例只用于表述模型，不对应实际平台合作关系。文中的“案例认知稿”“案例方案”和图示均指本文整理出的不同设计阶段，不指向某份未公开的外部文档。

文章讨论两个问题：平台如何识别跨业务经营的同一个客户，资质数据如何脱离入驻流程持续服务经营场景。客户部分涉及三层 ID 体系；资质部分涉及入驻、经营、变更、供给和消费，以及这些材料在四色模型中的位置。

:::

## 客户平台与资质中心

## 一、两个领域的边界

### 1.1 同一个经营主体，两套业务 ID

苹果品牌经营主体进入平台后申请两项业务：

- 申请成为电商商家，审核通过后创建苹果官方旗舰店；
- 申请成为商业化广告主，审核通过后创建广告账户。

如果从现有系统出发，电商看到的是 `shop_id`，商业化看到的是 `account_id`。两个 ID 分别能支持开店和投放，却没有回答一个平台级问题：这两个业务对象是否属于同一个合作主体？

平台签约、主体风险、跨业务服务和经营分析都依赖一个稳定的合作对象。店铺会关闭，广告账户会停用，管理员会更换，苹果品牌经营主体仍然存在。

::: tip

**统一客户平台：**平台服务的客户、客户参与的业务，以及统一客户 ID、业务客户 ID 和业务 ID 之间的关系。

:::

### 1.2 客户资料与资质数据

电商开店需要营业执照和商标注册证，商业化开户也会核验主体材料。把证照字段直接放进客户对象，短期内可以完成审核。业务扩展后，会遇到另一组问题：

- 同一份营业执照在电商和商业化重复提交；
- 营业执照变更时，新版本审核期间旧版本仍要继续使用；
- 商标注册证、品牌授权书等证明具有不同字段和有效期；
- 有些证明属于企业，有些证明只属于某个店铺或业务身份；
- 证明失效后，客户仍然存在。

这些问题都围绕证明的定义、归属、版本和有效性，与客户识别和业务身份使用不同的语言。

::: tip

**资质中心：**资质主体拥有的资质实例、实例所属类型、当前状态，以及修改内容与快照、申请单之间的关系。

:::

### 1.3 独立变化的两个领域

<tr><td>稳定对象</td><td>平台合作客户</td><td>一份具体证明</td></tr>
<tr><td>主要变化</td><td>识别客户、开通身份、绑定业务 ID、账号授权</td><td>提交、审核、生效、变更、过期、失效</td></tr>

</table>

两组对象没有共同状态机，也不共享事务。统一客户平台提供 `customer_id` 与 `biz_customer_id`；资质中心通过 `related_entity_type + related_entity_id` 引用资质主体。客户和资质可以独立变化，组织和部署方式也可以分别安排。

```text
客户平台                                      资质中心
┌────────────────────────┐                  ┌────────────────────────┐
│ 客户与业务身份          │                  │ 资质定义与实例          │
│ 业务 ID 关系            │── 主体引用 ────▶│ 版本、审核与有效性      │
│ 账号授权                │◀── 状态事件 ────│ 供给与消费              │
└────────────────────────┘                  └────────────────────────┘
```

## 二、统一客户平台的三层 ID 体系

### 2.1 银行业务中的 ID 职责迁移

案例先用银行业务说明 ID 职责如何分化。早期模型把余额、用户信息和交易记录都放在 Card Number 下：

![演进图 1：Card Number 同时承担凭证、客户、账户和交易入口职责。](/images/domain-modeling-practice/bank-card-number-model.svg)

加入网银后，Login ID 负责登录；继续追问“没有网银的人能否成为客户”，模型中又出现 Customer ID，用户信息从 Card Number 和 Login ID 迁到客户层。

![演进图 2：引入 Customer ID 后，客户身份从 Login ID 与 Card Number 中稳定下来。](/images/domain-modeling-practice/bank-customer-id-model.svg)

换卡、联名账户和共享余额继续暴露 Card Number 承载过多的问题，于是增加 Account ID。余额、额度和交易记录进入账户层，Card Number 只保留物理凭证职责。

![演进图 3：Customer ID、Account ID、Card Number 分别表达客户、业务账户和物理凭证。](/images/domain-modeling-practice/bank-three-level-id-model.svg)

场景增加后，原有 ID 的职责开始分化。Login ID 表达登录关系，Customer ID 表达客户，Account ID 承载余额、额度和交易记录，Card Number 回到物理凭证的位置。平台客户体系也面临类似的职责拆分。

### 2.2 UID 与店铺

平台只有电商开店时，`uid` 同时表示登录者和商家，店铺也直接挂在 `uid` 下。

```text
uid U01
  ├── 企业名称、营业执照、联系人（现状中错误挂载）
  └── shop_id SH01（苹果官方旗舰店）
```

这个模型能够支持一次开店，也隐含了三条商业规则：一个账号代表一个经营主体；一个主体只有一个管理员；换账号相当于更换经营主体。业务简单时，这些规则暂时不会造成明显问题。

### 2.3 电商客户与广告客户

苹果品牌经营主体还要投广告。商业化系统创建自己的账号和广告主资料后，平台内出现两个苹果客户，营业执照与联系人也被录入两次。

<table>
<tr><th>当前设计</th><th>新场景暴露的问题</th><th>隐含的商业规则</th></tr>
<tr><td><code>uid → shop_id</code></td><td>广告业务无法确认电商商家与广告主属于同一企业</td><td>客户由单项业务分别创建</td></tr>
<tr><td>主体资料挂在 <code>uid</code></td><td>两个业务重复采集主体资料</td><td>登录账号决定现实主体是谁</td></tr>
</table>

问题的稳定部分是现实经营主体。账号只负责登录，店铺和广告账户是业务对象。引入统一客户 ID 后，主体识别信息从账号和店铺迁移到 `customer_id`。

```text
                 统一客户 ID：customer_id=C1001
                 主体识别信息
                    /          \
                   /            \
            uid U01              account_id A8001
               │
          shop_id SH01
```

更换登录账号时 `customer_id=C1001` 不变；开通广告业务时也沿用这个客户 ID。账号和业务发生变化，客户标识保持稳定。

### 2.4 客户 ID 与业务身份

把银行模型映射到平台，主体资质是识别现实经营主体的重要证据，但不是客户本身。一个客户可以关联多种身份识别材料及其历史版本，业务资质也可以有多份；`customer_id` 标识归一后的现实主体，即使某份资质过期，客户记录仍然存在。

![识别与经营分工：身份资质确认客户是谁，业务资质说明客户能够经营什么。](/images/domain-modeling-practice/customer-qualification-model.svg)

案例中的阶段性客户 ID 认知稿继续把 ShopID、AuthorID、广告账户 ID、合同和账号放到客户 ID 周围，形成关系全景：

![以 Customer ID 为关系锚点，账号、资质、业务对象与商业关系沿各自生命周期变化。](/images/domain-modeling-practice/customer-centered-final-model.svg)

图中的登录账号、客户和业务对象各有自己的 ID，客户 ID 位于跨业务关系的中心。统一客户平台又增加了一层业务身份，用来容纳商家、达人、服务商、广告主和代理商之间的差异。

::: info

**两个设计阶段：**

认知层模型用于解释商业对象和挂载关系：`资质 ID → 客户 ID → ShopID / AuthorID / 广告账户 ID`。

平台化落地模型用于明确系统建设与业务接入：`主体资质 → customer_id → biz_customer_id → biz_id`。

后者延续了以客户 ID 为中心的原则，并把业务身份显式建模为业务客户 ID。

:::

统一客户平台还要容纳不同业务身份。客户在电商中可能是商家、达人或服务商，在商业化中可能是广告主或代理商。每种身份有自己的注册过程和资产范围。业务 ID 全部直挂 `customer_id` 时，这些差异都会堆积在客户层。

业务客户 ID 位于统一客户 ID 与业务 ID 之间，三层关系如下：

```text
主体资质
   │ 1:1 识别物理世界主体
   ▼
统一客户 ID：customer_id = C1001
   ├── 业务客户 ID：biz_customer_id = EC2001（电商商家）
   │      ├── seller_id = S01
   │      ├── shop_id = SH01
   │      └── shop_id = SH02
   └── 业务客户 ID：biz_customer_id = AD3001（商业化广告主）
          ├── account_id = A8001
          └── account_id = A8002
```

`biz_customer_id` 是客户在某个业务场景下的身份标识。业务身份管理负责该身份的定义和注册；具体业务负责 `biz_customer_id` 与自身业务 ID 的映射。业务 ID 仍在电商、商业化等业务域内运行，统一客户平台不会替换原有 ID 体系。

### 2.5 三层 ID 的原始定义

<table>
<tr><th>层级</th><th>技术方案中的定义</th><th>业务方感知</th></tr>
<tr><td>统一客户 ID<br><code>customer_id</code></td><td>标识归一后的现实经营主体，可关联多份识别材料，不随单项业务或单份资质变化</td><td>业务方不强感知，用于跨业务归一客户与共享客户级资产</td></tr>
<tr><td>业务客户 ID<br><code>biz_customer_id</code></td><td>客户在不同业务场景下的身份定义</td><td>业务方需要感知，用于业务身份注册及资产绑定</td></tr>
<tr><td>业务 ID<br><code>biz_id</code></td><td>业务基于业务客户 ID 衍生的模型 ID</td><td>由各业务域维护，并建立与 <code>biz_customer_id</code> 的映射</td></tr>
</table>

资产挂载层级决定复用范围。需要跨业务共享的主体资质应挂在 `customer_id`；只在电商商家身份下共享的数据挂在对应的 `biz_customer_id`；店铺商品、广告物料等业务资产继续挂在 `shop_id`、`account_id` 等业务 ID 下。

### 2.6 统一 B 端账号与三层 ID 分工

统一客户 ID 解决“客户是谁”，统一 B 端账号解决“谁登录并管理客户”。两套 ID 不能合并。企业管理员离职或账号受处罚时，客户、业务客户和业务资产仍应存在。

```text
统一 B 端账号 Bid B01 ──管理──▶ customer_id C1001
业务管理员 / 业务子账号 ───────▶ 对应业务客户及业务系统

customer_id C1001 ──拥有──▶ biz_customer_id EC2001
biz_customer_id EC2001 ──映射──▶ seller_id / shop_id
```

统一客户平台负责 B 端账号的登录、组织管理和子账号基础能力。电商上传商品、商业化创建投放等业务权限仍由各业务域授权。客户关系平台则保存 Bid 与业务 ID、跨业务 ID、客户与客户之间的绑定关系，提供绑定、解绑以及正反向寻址。

### 2.7 统一客户平台总体模型

统一客户平台规划把这些关系放进一张总图：统一客户 ID、业务客户 ID 和业务 ID 纵向排列，左侧是统一 B 端账号，右侧是业务身份管理和用户资产。

![统一客户 ID 体系规划总图：主体资质识别统一客户，业务客户 ID 表达业务身份，各业务 ID 继续由业务域维护。](/images/domain-modeling-practice/unified-customer-platform-model.svg)

图中的三层 ID 各自承载不同信息：UID 与客户分离，业务客户 ID 容纳各业务身份，业务 ID 保留在业务域内；统一 B 端账号负责跨业务登录和管理。

<tr><th>建设内容</th><th>案例方案职责</th><th>边界</th></tr>

<tr><td>业务身份管理</td><td>定义和注册客户在各业务域中的身份</td><td>具体经营规则仍在业务域</td></tr>

<tr><td>客户关系平台</td><td>维护 ID 类型、业务场景、绑定关系及正反向寻址</td><td>只保存关系，不承载业务对象数据</td></tr>
<tr><td>统一资产管理</td><td>主体资质等客户级资产可以跨业务复用</td><td>业务流强相关资产继续留在业务域</td></tr>
</table>

案例认知稿把客户 ID 放在跨业务关系的中心；后续平台化规划在其上下增加业务客户 ID、统一 B 端账号和关系平台。两版模型处于不同设计阶段，登录账号、客户、业务身份和业务对象的职责划分保持一致。

## 下篇：资质业务与四色视角

## 四、资质从入驻资料中独立出来

资质最早依附于商家入驻。经营场景增多后，它的归属、变化和使用方式逐渐超出入驻申请单的范围。

### 4.1 资质还是入驻申请单中的字段

电商早期只有商家入驻。企业填写申请单，上传营业执照，平台审核通过后创建店铺。最直接的设计是把证照数据放在入驻申请单中：

```text
商家入驻申请单 A100
  ├── 申请人
  ├── 店铺信息
  ├── 营业执照字段
  ├── 商标注册证字段
  └── 审核状态
```

入驻平台在这里承担资质采集方的角色。商家提交营业执照、商标注册证等材料，用来证明经营主体满足平台的合规准入要求。资质数据跟随入驻申请进入审核流程，最初的使用范围也集中在准入环节。

### 4.2 从合规准入到经营证明

店铺开通后，营业执照开始用于商家证明公示和资金进件，品牌资质用于品牌商品发布，行业资质和类目资质用于发品校验。资质的使用范围从合规准入延伸到日常经营，更新、过期和失效也发生在入驻流程结束之后。

<table>
<tr><th>业务场景</th><th>资质作用</th><th>与入驻流程的关系</th></tr>
<tr><td>商家入驻</td><td>主体资质、品牌资质证明商家符合合规准入条件</td><td>入驻平台采集材料并发起审核</td></tr>
<tr><td>商家证明公示</td><td>主体资质持续向消费者展示商家身份</td><td>店铺开通后仍需长期读取，内容也可能更新</td></tr>
<tr><td>发布品牌商品</td><td>品牌资质证明商家拥有品牌经营权</td><td>资质可能在经营期间新增、续期或失效</td></tr>
<tr><td>特定类目发品</td><td>行业资质、类目资质证明商家具备经营资格</td><td>经营范围变化会带来新的资质要求</td></tr>
<tr><td>资金进件</td><td>主体资质用于支付和结算侧核验</td><td>资金系统持续查询，不依赖入驻申请单结构</td></tr>
</table>

入驻平台负责采集准入材料并发起审核；资质中心承接审核后的长期存续，管理经营期间的更新、续期、过期和失效，并向证明公示、发品校验、资金进件等场景提供查询。两者在合规准入阶段协作，店铺开通后各自沿不同生命周期运行。

### 4.3 五大类、220 多种资质

资质独立后，早期方案可以按主体资质、品牌资质、行业资质、类目资质和商品资质分别建表、写接口。随着业务发展，资质达到五大类、220 多个具体类型，新增一种资质就要增加表结构、接口和页面逻辑。

```text
主体资质表 ── 主体资质接口
品牌资质表 ── 品牌资质接口
行业资质表 ── 行业资质接口
类目资质表 ── 类目资质接口
商品资质表 ── 商品资质接口

新增资质类型 → 增加模型、表、接口和审核逻辑
```

这些资质的差异主要在字段结构、归属主体、校验方式和展示样式，保存、送审、查询、生效和失效的过程大体相同。模型中出现了三类描述性概念：

- **资质类型**：描述资质是什么、归属哪类主体、包含哪些字段、支持哪些校验；
- **资质分类**：聚合多个资质类型，例如品牌资质分类；
- **元数据配置**：用 JSON Schema 等方式描述字段和表单。

新增资质由代码开发转成资质类型和元数据配置，保存与审核沿用公共能力。

### 4.4 资质究竟属于谁

电商现状中，主体资质和品牌授权常挂在店铺维度。同一个苹果品牌经营主体开两家店，或同时进入商业化时，营业执照会被重复上传和审核。品牌授权本来授予某个营业执照主体，挂在单一店铺后也无法自然复用。

<table>
<tr><th>挂载方式</th><th>表达的业务含义</th><th>出现的问题</th></tr>
<tr><td>所有资质挂店铺</td><td>资质只属于某一家店</td><td>主体资质跨店铺、跨业务重复</td></tr>
<tr><td>所有资质挂统一客户 ID</td><td>同一客户下所有业务身份都可使用</td><td>业务身份专属经营资质范围过大</td></tr>
<tr><td>按资质实际归属挂载</td><td>主体层复用，业务身份层隔离</td><td>需要统一表达不同类型的挂载对象</td></tr>
</table>

模型中用两个概念表达归属：

- **资质主体类型**：统一客户 ID、业务客户 ID 或扩展业务主体；
- **资质主体**：主体类型下的具体 ID，例如 `customer_id=C1001`。

资质中心通过 `related_entity_type + related_entity_id` 引用主体，不维护客户和业务客户的主体表。资产挂在哪一层，决定它可以在哪些场景中复用。

### 4.5 生效数据与待审数据并存

**资质实例**表示某个主体持有的一份具体资质。同一主体可以拥有多份同类型资质，例如多个商标注册证或不同品牌范围的授权；因此主体类型、主体 ID 和资质类型只确定业务归属，还需要实例 ID 或证照号、品牌、适用范围等业务键区分具体实例。营业执照地址变更后，同一实例的读取和修改会同时发生：

```text
当前营业执照已生效
       │
       ├── 店铺亮证继续读取旧地址
       ├── 资金进件继续读取旧地址
       └── 管理员提交新地址，等待审批
```

模型需要同时保存两类事实：当前生效数据继续服务，本次修改内容处于审批中。对应的数据结构也分成两套：

<table>
<tr><th>模型</th><th>案例状态</th><th>职责</th></tr>
<tr><td>资质实例</td><td>初始化、已生效、已失效</td><td>保存当前对外服务的数据及有效期</td></tr>
<tr><td>资质快照</td><td>已保存、审批中、审批通过、审批拒绝</td><td>保存草稿、本次修改和历史镜像</td></tr>
<tr><td>申请单 / 审核单</td><td>由申请单域和审核中心管理</td><td>记录送审过程并承接审核交互</td></tr>
</table>

快照审批通过后更新资质实例；审批拒绝时，当前生效实例保持不变。有效性属于实例，审批状态属于快照。

### 4.6 页面、接口和离线数据

资质数据的来源继续扩展：商家在页面填写，外部系统实时调用接口，历史数据通过离线任务迁移。如果按业务身份分别开发，商家、达人、服务商、商业化都要重复建设接入链路。

案例方案将来源收敛成三种**资质供给方式**：

- JSON Schema 可视化收集：资质中心托管表单和完整生命周期；
- 开放接入：外部系统通过 RPC 实时写入；
- 离线供给：历史迁移或周期性同步。

三种路径最后进入同一套资质实例和快照模型。业务差异留在供给配置中，生命周期能力得以复用。

### 4.7 资质的下游使用

资质中心有了统一存储，下游仍可能直接按表结构查询。发品、亮证、资金进件和广告开户会各自理解资质类型、实例状态和字段结构，存储模型随之扩散到所有调用方。

资质消费包含两个问题：

1. 某个业务场景需要哪些资质类型；
2. 当前资质主体是否拥有满足条件的有效实例。

案例方案据此引入：

- **业务实体**：规则作用的外部对象，例如商品类目；
- **资质关联规则**：业务实体需要哪些资质类型及其约束；
- **资质消费能力**：提供在线/离线查询和规则校验，隔离内部存储。

```text
业务实体：某商品类目
       │
       └── 资质关联规则
             ├── 要求行业许可证
             ├── 要求类目经营资质
             └── 查询资质主体的有效实例
```

<table>
<tr><th>业务现象</th><th>模型概念</th></tr>
<tr><td>资质从合规准入延伸到证明公示、发品和资金等经营场景</td><td>独立的资质中心与资质生命周期</td></tr>
<tr><td>五大类、220+ 类型持续扩张</td><td>资质类型、资质分类、元数据配置</td></tr>

### 5.1 四类业务材料

<table>
<tr><th>颜色</th><th>原型</th><th>资质业务中的内容</th></tr>
<tr><td style="background:#fee2e2">红</td><td>Moment-Interval</td><td>资质采集、实时/周期供给、保存、提审、审核、撤回、生效、查询、规则校验、核验、巡检、过期、治理清退和失效，以及资质的有效区间</td></tr>
<tr><td style="background:#fef3c7">黄</td><td>Role</td><td>资质供给方、申请人、资质持有人、审核方和资质使用方</td></tr>
<tr><td style="background:#d1fae5">绿</td><td>Party-Place-Thing</td><td>资质主体、资质实例、资质快照、资质审核单、证照文件和业务实体</td></tr>

案例技术方案中的资质实例、资质快照和资质审核单都有独立标识，可以保存和关联，属于绿色 PPT。保存、提审、审核、生效和失效则是发生在这些对象上的红色 MI。

### 5.2 绿色 PPT：资质业务中的对象

<table>
<tr><th>绿色对象</th><th>案例含义</th><th>主要关系</th></tr>
<tr><td>资质主体</td><td>资质归属的具体对象，例如 <code>customer_id=C1001</code> 或某个 <code>biz_customer_id</code></td><td>一个主体可以拥有多条资质实例</td></tr>
<tr><td>资质实例</td><td>某个资质主体针对某个资质类型的一条具体资质</td><td>引用主体与资质定义，并拥有多个快照</td></tr>
<tr><td>资质快照</td><td>资质实例的草稿、本次修改内容或历史镜像</td><td>归属于资质实例，并参与送审</td></tr>
<tr><td>资质审核单</td><td>资质送审后形成的流程记录，用于与申请单域、审核中心交互</td><td>关联一个或多个快照，保存一次审核上下文</td></tr>
<tr><td>证照文件</td><td>营业执照图片、商标注册证文件等资质材料</td><td>作为实例或快照数据的一部分保存</td></tr>
<tr><td>业务实体</td><td>消费规则作用的外部对象，例如店铺、商品类目或活动</td><td>通过资质关联规则连接资质类型</td></tr>
</table>

```text
资质主体
   │ 1..n
   ▼
资质实例 ── 1..n ──▶ 资质快照 ◀── m..n ──▶ 资质审核单
   │                       │
   │                       └── 本次提交的证照字段与文件
   │
   └── 归属一个资质定义

业务实体 ── 资质关联规则 ──▶ 资质定义
```

案例材料区分“申请单”和“资质审核单”：申请单由外部申请单域提供，记录一次业务申请；领域模型图中的资质审核单关联本次送审的一份或多份资质快照；审核操作由审核中心执行。三者共同组成审批链路。

资质快照不是一次“审核通过”事件，它保存草稿、待审内容和历史镜像；资质审核单也不是“审核”动作本身，而是审核流程留下的业务记录。对象和过程分开后，实例状态与快照审批状态也各有归属。

### 5.3 红色 MI：对象经历的过程

<table>
<tr><th>红色过程</th><th>涉及的绿色对象</th><th>结果</th></tr>
<tr><td>资质采集与保存</td><td>资质主体、资质实例、资质快照</td><td>新建实例或保存草稿快照</td></tr>
<tr><td>资质提审</td><td>资质快照、资质审核单</td><td>快照进入审批中，审核单记录本次流程</td></tr>
<tr><td>审核通过</td><td>资质审核单、资质快照、资质实例</td><td>快照标记审批通过，数据写入实例，实例生效</td></tr>
<tr><td>审核拒绝</td><td>资质审核单、资质快照</td><td>快照标记审批拒绝，当前生效实例保持不变</td></tr>
<tr><td>撤回与修改</td><td>资质审核单、资质快照</td><td>结束本次送审，快照回到可修改状态</td></tr>
<tr><td>资质查询与规则校验</td><td>业务实体、资质主体、资质实例</td><td>按业务实体关联的规则查询有效实例，返回资格判断</td></tr>
<tr><td>资质核验与巡检</td><td>资质实例、证照文件</td><td>校验实例数据、有效期和外部证明，异常时进入治理或失效处置</td></tr>
<tr><td>过期或治理失效</td><td>资质实例</td><td>实例从已生效变为已失效</td></tr>
</table>

```text
快照：已保存 ──提审──▶ 审批中 ──通过──▶ 审批通过
                         │
                         ├──拒绝──▶ 审批拒绝
                         └──撤回──▶ 可修改

实例：初始化 ──快照审批通过──▶ 已生效 ──过期/治理──▶ 已失效
                    │
                    └── effective_start_time / effective_end_time
```

案例分别定义了实例状态和快照状态。实例表达当前资质是否对外有效，快照表达一份提交内容处于什么审批阶段。审核单保存过程记录，审核中心执行审核操作。

### 6.2 资质基础、供给和消费

## 七、业务变化在模型中的落点

几个常见变化在模型中的影响范围如下：

- 资质主体类型、资质主体 ID 和资质类型共同确定实例的业务归属；实例 ID 或证照号、品牌、适用范围等业务键区分同类型的多份实例；
- 资质实例保留当前对外服务的数据，状态为初始化、已生效或已失效；
- 每次保存或修改形成资质快照，审批结论绑定快照；
- 快照审批通过后更新实例，审批拒绝不覆盖当前生效实例；
- 资质主体来自统一客户平台或外部业务键，资质中心只保存引用；
- 业务实体通过资质关联规则连接资质类型，消费方无需理解资质的供给过程。

## 结语

客户体系围绕几个长期存在的问题展开：平台服务的是谁，客户进入了哪些业务，资产归属统一客户 ID、业务客户 ID 还是业务 ID，登录账号与业务账户是什么关系。案例认知稿以客户 ID 为中心组织这些对象；平台化规划补充了业务客户 ID、统一 B 端账号和客户关系平台。

资质最初由入驻平台采集，用来证明商家满足合规准入条件。店铺开通后，主体资质进入商家证明公示和资金进件，品牌、行业及类目资质也被经营场景持续使用。它们的更新、续期、过期和失效跨越了入驻申请单的生命周期，长期存续和消费由资质中心承接。

四色建模把资质材料分成四类：资质主体、资质实例、资质快照、资质审核单和业务实体属于绿色对象；采集、保存、提审、审核、生效和失效属于红色过程；供给方、申请人、持有人、审核方和使用方属于黄色角色；主体类型、资质定义、分类、供给方式、业务定义和规则定义属于蓝色描述。
